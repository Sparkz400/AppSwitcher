# Add from an open window

In Settings, choose **Add app → Add from an open window**. Compact layouts expose the same command under **Actions**. Filter the current windows, select one, review its executable and edit the proposed app name if needed, then choose **Add app**. Normal Save/Undo behavior applies. Cancel creates no entry. **Enter manually** preserves the existing setup flow.

## Behavior

- Discovers visible top-level application windows on the current desktop, including minimized windows. Excludes AppSwitcher, shell surfaces, tool/no-activate/child windows, cloaked windows, conventional dialogs and owned windows that do not explicitly identify as app windows. Temporary windows that disappear later fail acceptance revalidation.
- Reads the executable and process creation time with limited-information process access. Inaccessible windows remain identifiable by their title, with a manual setup fallback; no elevation is requested. Generic script/runtime hosts, Store/packaged executables and known unsupported browsers require manual settings.
- Before acceptance, rereads the window handle's PID, process creation time and executable. A recycled PID, changed path, closed window or lost access prevents importing the stale selection. Document-title changes are allowed because the selected object is an application, not a particular document.
- Prefills the executable and a name derived from its filename. Keeps the normal executable-scoped matching and working-folder fallback; does not copy the current document title into `WinPattern`, scrape arguments, capture document paths, or persist PID/window handles. It does not open, close, focus or restart the chosen program. Autostart and watchdog stay off; destructive-action confirmation stays on. Apps that require arguments can be adjusted in the existing settings editor.
- An existing native entry with the same normalized absolute executable path is selected without changing its settings. Multiple existing entries require choosing one in Applications. Filename-only aliases and unresolved paths are not treated as proven identity matches. Names remain unique when a new entry is created.
- Chrome, Edge and Firefox windows offer **Set up website**. This creates a website draft with the corresponding browser and focuses its address field; the user supplies the URL and paired profile through the existing managed-tab flow. A window title is never used to infer a URL or attach an existing tab. Native browser-process import is rejected.
- Admin rights are checked when opening and again after asynchronous validation and immediately before applying a result. Closing the picker or expiring the session cancels/discards pending work; late results cannot create an app. Selection/name editing is disabled during native reads and a changed selection cannot accept an earlier result.

## Cost and native API choices

No dependencies, startup services, helpers, timers, WMI queries or subscriptions to foreign processes are added. The catalog is created only for the dialog. Each explicit scan runs off the UI thread and releases its process handles immediately; the virtualized list owns its snapshot until close. Icons are copied from window-class handles where available, frozen for WPF and the copied native handles destroyed. A generic icon covers missing icons. Executable files and network shares are not opened to extract icons or version metadata.

The implementation uses [EnumWindows](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-enumwindows) for top-level enumeration, [QueryFullProcessImageName](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-queryfullprocessimagenamew) and [GetProcessTimes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes) for executable/process identity. Foreign-window captions use [GetWindowText](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getwindowtextw), whose cross-process caption behavior avoids sending a blocking text request to an unresponsive application. It does not send `WM_GETICON` or inspect other apps' controls.

## Verification

- Unit coverage: native/browser/runtime classification, process birth/path/handle checks, changing document titles, filtering/name retention, duplicate changes during acceptance, authority revocation, late scan/acceptance completion, selection changes and inaccessible-app fallback.
- Native checks: a separately launched synthetic WPF application is discovered, minimized, retitled and closed. A minimized window remains selectable and the closed window cannot pass revalidation. The test child is always cleaned up. Native scan timing is recorded in `artifacts/ui-checks/window-picker-native.json`; no titles or paths of the user's other windows are written to that report.
- WPF checks: English/German, light/dark, 780×640 and 600×480 dialogs, touch targets, search/empty selection, browser routing, duplicate presentation, Add app menu, actual modal cancellation, safe import defaults, and session expiry closing both picker and privileged editor. Screenshots use synthetic candidates in `artifacts/ui-checks/window-picker-*.png`.
- Production settings are not changed by these checks. Real browser tab control and industrial application behavior continue to use their existing services; this feature does not change matching after setup.

The release passed **185 unit/integration tests** and **3,658 native UI assertions** with no WPF binding warnings. The focused modal-lifetime regression can be run with `dotnet run --project AppSwitcher.UiChecks -c Release -- --picker-expiry-check`. It covers both explicit owner close and session expiry: the picker must close first and release its modal dispatcher frame, rather than leaving an invisible modal operation behind. The measured native snapshot took approximately **1.9 ms** in one local run; this is not an upper bound for all desktops.

A production observation with the existing configuration unchanged and settings closed measured **64.0 MiB median private memory**, **125.0 MiB working set**, **4.74% of one core / 0.22% of this 22-logical-processor machine**, and **1,566 ms to a visible launcher**. Sampling lasted 60 seconds after a 10-second settle. This single local launch is not a cold-start benchmark or a controlled before/after comparison; managed applications and browser/native-host processes are excluded. Raw data: `artifacts/window-picker-work/production-performance.json`.
